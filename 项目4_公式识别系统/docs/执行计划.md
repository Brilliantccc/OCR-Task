## 2. 技术方案选型

### 2.1 整体架构：Encoder-Decoder + Attention

```
┌──────────────┐      ┌──────────────────┐      ┌──────────────┐
│   Encoder    │ ──▶  │  Attention Layer  │ ──▶  │   Decoder    │
│  (CNN/ViT)   │      │  (Bahdanau/      │      │  (LSTM/      │
│              │      │   Cross-Attn)    │      │   GRU)       │
└──────────────┘      └──────────────────┘      └──────────────┘
      图像特征              上下文向量              LaTeX token
```

### 2.2 方案对比与选择

| 方案 | Encoder | Decoder | 优点 | 缺点 | 预期 BLEU | 选择 |
|------|---------|---------|------|------|-----------|------|
| **A: CNN + LSTM** | ResNet-34 | LSTM + Bahdanau | 成熟稳定，显存友好 | 长公式效果一般 | 0.80~0.85 | ✅ **已实现**，现为基线 |
| **B: ViT + Transformer** | ViT-Base | GPT-2 风格 Transformer | 长序列更强，SOTA | 显存大，数据需求高 | 0.85~0.90 | ✅ **已实现**，现为默认架构（§4.6） |
| **C: Pix2Tex 微调** | ViT | Transformer | 开箱即用，预训练权重 | 词表小(~80)，定制性低 | 0.85~0.87 | 未采用 |

> ⚠️ **编号注意**：本表的 A/B/C 与 §9.2 的"备选 A/B/C"**不是同一套编号**——
> §9.2 的备选 C 指的是 §2.2 的方案 B（ViT + Transformer）。阅读时以描述为准。

**最终选择：两套都实现，默认 ViT + Transformer**

原计划选定方案 A（ResNet-34 + LSTM + Bahdanau）作为主方案，理由是成熟稳定、显存友好：

- ResNet-34 参数量 ~21M，公式图像特征提取足够
- LSTM 对序列建模成熟，配合 Teacher Forcing 训练高效
- Bahdanau（加性）Attention 适合图像-序列对齐
- 参考：im2markup (Harvard NLP) 采用 CNN+LSTM 路线，BLEU 可达 0.82+

**但实现阶段发现方案 A 有一个结构性缺陷**：编码器用
`AdaptiveAvgPool2d((1, None))` 把高度方向压成 1，而 H=64 时 layer4 输出本来
只剩 `(B,512,2,W/32)` 的 2 行，还要再平均掉。数学公式里 `x^2` 与 `x_2`
**字形完全相同、只差垂直位置**——高度一平均，这个唯一的区分信号就没了。

> 实测（随机初始化编码器，仅说明架构倾向）：
> `x^2` vs `x_2` 的特征余弦相似度 **0.9998**，而两个完全不同的公式是 0.7529。

因此改为**双架构并存**：`vit_transformer`（方案 B，默认）与 `cnn_lstm`（方案 A，保留作
A/B 对比基线），通过 `config.MODEL_ARCH` 切换。这样既解决了架构缺陷，
又保留了验证"换架构到底提升多少"的能力。

### 2.3 LaTeX Tokenizer 设计

**核心原则**：将 LaTeX 字符串拆分为有意义的 token 单元

```python
# Token 类型示例
# - 单字符:    a, b, x, +, =, 1, 2
# - 命令:      \frac, \sqrt, \sum, \int, \alpha, \beta
# - 环境:      \begin, \end, {, }
# - 特殊:      <SOS>, <EOS>, <PAD>, <UNK>
```

| 项目 | 规划值 | **实测值** |
|------|--------|-----------|
| 词表大小 | 500 ~ 800 tokens | **245**（全部标签文件的不同 token 总数） |
| 最大序列长度 | 150 ~ 200 tokens | 中位 17 / P95 41 / P99 57 / max 186，200 覆盖 100% |
| 特殊 token | `<PAD>=0`, `<SOS>=1`, `<EOS>=2`, `<UNK>=3` | 一致 |

> **词表规划值高估了**：既然是"命令级 + 字符级"的混合分词，
> `\frac` 是一个 token 而字母 `a`/`b` 各是一个 token，词表天然很小。
> 实测 `MIN_FREQ=2` 只丢弃 49 个 token、占比 **0.00%**，
> 所以词表**不是**本项目的瓶颈，无需为它做任何优化。
> （文档 §2.3 里"参考规模 CROHME 词表 ~100-300"这一行才是准确量级。）

**Tokenizer 实现要点**：
1. 正则匹配 LaTeX 命令：`\\[a-zA-Z]+` 匹配命令，`[^a-zA-Z\\]` 匹配单字符
2. 保留空格语义（`\ `, `\quad` 等）
3. 支持 `unk_token` 处理未见过的符号
4. 序列长度截断 + padding 对齐
5. **词表构建**：从训练集统计，出现次数 < N 的替换为 `<UNK>`

```python
import re
def latex_tokenizer(formula):
    """正则分词：命令(\frac) | 括号({}[]) | 单字符(a,+,1) | 其他符号"""
    return re.findall(
        r'\\[a-zA-Z]+|[{}()\[\]]|[a-zA-Z0-9]|[^\\a-zA-Z0-9{}()\[\]\s]',
        formula
    )
```

> 参考规模：CROHME 词表 ~100-300，im2latex-100K 词表 ~500-700，TexTeller ~21000（覆盖稀有命令）。

### 3.3 CROHME INKML 处理

**关键步骤**：
1. 解析 XML 中的 `<trace>` 元素获取笔迹坐标
2. 使用 `matplotlib` 或 `PIL` 将笔迹渲染为灰度图像
3. 提取 `<annotation>` 中的 LaTeX 标签
4. 处理多行公式、空公式等边界情况

```python
# INKML 解析伪代码
def parse_inkml(filepath):
    tree = ET.parse(filepath)
    root = tree.getroot()
    ns = {'ink': 'http://www.w3.org/2003/InkML'}

    # 提取笔迹
    traces = []
    for trace in root.findall('.//ink:trace', ns):
        points = trace.text.strip().split(',')
        coords = [(float(p.split()[0]), float(p.split()[1])) for p in points]
        traces.append(coords)

    # 提取 LaTeX 标签
    latex = root.find('.//ink:annotation[@type="truth"]', ns).text

    # 渲染为图像
    image = render_traces(traces, image_size=(224, 224))
    return image, latex
```

## 4. 模型架构设计

### 4.1 Encoder：ResNet-34 特征提取器

```python
class FormulaEncoder(nn.Module):
    """
    基于 ResNet-34 的公式图像编码器
    输入: (B, 1, H, W) 灰度公式图像
    输出: (B, C, h, w) 空间特征图
    """
    def __init__(self, pretrained=True):
        super().__init__()
        resnet = torchvision.models.resnet34(pretrained=pretrained)
        # 修改第一层：灰度图单通道输入
        self.conv1 = nn.Conv2d(1, 64, kernel_size=7, stride=2, padding=3, bias=False)
        # 提取中间层特征（去掉 avgpool 和 fc）
        self.layer0 = nn.Sequential(self.conv1, resnet.bn1, resnet.relu, resnet.maxpool)
        self.layer1 = resnet.layer1  # 64 通道
        self.layer2 = resnet.layer2  # 128 通道
        self.layer3 = resnet.layer3  # 256 通道
        self.layer4 = resnet.layer4  # 512 通道
        self.adaptive_pool = nn.AdaptiveAvgPool2d((1, None))  # 高度压缩为1，宽度保留

    def forward(self, x):
        x = self.layer0(x)    # (B, 64, H/4, W/4)
        x = self.layer1(x)    # (B, 64, H/4, W/4)
        x = self.layer2(x)    # (B, 128, H/8, W/8)
        x = self.layer3(x)    # (B, 256, H/16, W/16)
        x = self.layer4(x)    # (B, 512, H/32, W/32)
        x = self.adaptive_pool(x)  # (B, 512, 1, W')
        x = x.squeeze(2)      # (B, 512, W') — 展平空间维度
        x = x.permute(0, 2, 1)  # (B, W', 512) — 序列形式
        return x
```

**设计要点**：
- 灰度输入：公式图像无需 RGB 三通道
- `AdaptiveAvgPool2d(1, None)`：高度压缩为 1，保留宽度方向的序列信息
- 输出形状 `(B, T_enc, 512)` 作为 Decoder 的记忆序列

### 4.2 Attention：Bahdanau 加性注意力

```python
class BahdanauAttention(nn.Module):
    """
    Bahdanau (加性) Attention
    encoder_output: (B, T_enc, enc_dim)
    decoder_hidden: (B, dec_dim)
    """
    def __init__(self, enc_dim, dec_dim, attn_dim=256):
        super().__init__()
        self.W_enc = nn.Linear(enc_dim, attn_dim, bias=False)
        self.W_dec = nn.Linear(dec_dim, attn_dim, bias=False)
        self.V = nn.Linear(attn_dim, 1, bias=False)

    def forward(self, encoder_output, decoder_hidden):
        # decoder_hidden: (B, dec_dim) → (B, 1, attn_dim)
        enc_proj = self.W_enc(encoder_output)   # (B, T_enc, attn_dim)
        dec_proj = self.W_dec(decoder_hidden).unsqueeze(1)  # (B, 1, attn_dim)
        scores = self.V(torch.tanh(enc_proj + dec_proj)).squeeze(-1)  # (B, T_enc)
        weights = F.softmax(scores, dim=-1)  # (B, T_enc)
        context = torch.bmm(weights.unsqueeze(1), encoder_output).squeeze(1)  # (B, enc_dim)
        return context, weights
```

### 4.3 Decoder：LSTM + Attention

```python
class FormulaDecoder(nn.Module):
    """
    基于 LSTM 的公式解码器
    使用 Bahdanau Attention 对齐编码器特征
    """
    def __init__(self, vocab_size, embed_dim=256, enc_dim=512,
                 dec_dim=512, attn_dim=256, dropout=0.3):
        super().__init__()
        self.embedding = nn.Embedding(vocab_size, embed_dim, padding_idx=0)
        self.attention = BahdanauAttention(enc_dim, dec_dim, attn_dim)
        self.lstm = nn.LSTM(embed_dim + enc_dim, dec_dim, batch_first=True)
        self.fc_out = nn.Linear(dec_dim + enc_dim + embed_dim, vocab_size)
        self.dropout = nn.Dropout(dropout)

    def forward_step(self, token, hidden, cell, encoder_output):
        """单步解码"""
        embedded = self.dropout(self.embedding(token))  # (B, embed_dim)
        context, attn_weights = self.attention(encoder_output, hidden[-1])
        lstm_input = torch.cat([embedded, context], dim=-1).unsqueeze(1)
        output, (hidden, cell) = self.lstm(lstm_input, (hidden, cell))
        output = output.squeeze(1)
        pred = self.fc_out(torch.cat([output, context, embedded], dim=-1))
        return pred, hidden, cell, attn_weights
```

### 4.4 完整模型：FormulaRecognizer

```python
class FormulaRecognizer(nn.Module):
    """
    Encoder-Decoder + Attention 公式识别模型
    训练时: Teacher Forcing (可配置比例)
    推理时: Beam Search / Greedy Decoding
    """
    def __init__(self, vocab_size, embed_dim=256, dec_dim=512, dropout=0.3):
        super().__init__()
        self.encoder = FormulaEncoder(pretrained=True)
        self.decoder = FormulaDecoder(vocab_size, embed_dim, 512, dec_dim, dropout=dropout)
        self.vocab_size = vocab_size

    def forward(self, images, targets=None, teacher_forcing_ratio=0.5):
        encoder_output = self.encoder(images)  # (B, T_enc, 512)
        if self.training and targets is not None:
            return self._decode_train(encoder_output, targets, teacher_forcing_ratio)
        else:
            return self._decode_inference(encoder_output)

    def _decode_train(self, encoder_output, targets, tf_ratio):
        """训练模式：Teacher Forcing + 随机采样"""
        B, T = targets.shape
        outputs = torch.zeros(B, T, self.vocab_size).to(encoder_output.device)
        # 初始化 decoder hidden state（用 encoder 输出的均值）
        hidden = encoder_output.mean(dim=1)  # (B, 512)
```

### 4.6 【已实现】ViT + Transformer 架构

即 §2.2 的方案 C，当前默认架构（`config.MODEL_ARCH = 'vit_transformer'`）。

#### 编码器：自写 ViT-B/16

**为什么不用 torchvision 的 `vit_b_16` 开箱**：它源码里是硬断言固定尺寸——

```python
torch._assert(h == self.image_size, f"Wrong image height! Expected {self.image_size} but got {h}!")
```

`forward` 没有位置编码插值入口；模块里那个 `interpolate_embeddings` 是 state_dict 级工具，
作用是把位置编码插值到**另一个固定尺寸**，仍要求最终尺寸固定。
而公式图像实测宽高比最高达 **16.38:1**（HME100K），固定方形输入会严重压扁。

**实现方式**：自建同构模块 + **逐块搬运**预训练权重。

```
FormulaViTEncoder
├── patch_embed   Conv2d(3, 768, k=16, s=16)   ← 逐块从 torchvision vit_b_16 拷贝
├── blocks        12 × ViTBlock(768, 12 heads) ← 同上（子模块命名对齐 ln_1/self_attention/ln_2/mlp.0/mlp.3）
├── norm          LayerNorm(768)                ← 同上
└── pos_embed     2D sin-cos，按实际网格现场生成  ← 自己实现，分辨率无关
```

输入 `(B,1,64,W)` 复制成 3 通道（完整保留 ImageNet 预训练权重，比改 patch-embed 卷积核更简单），
patch=16 → 网格 `4 × (W/16)`。典型 52~68 个 patch，W=1200 时 300 个。

**逐块拷贝而非整体 `load_state_dict` 的两个理由**：
1. 要丢掉 `class_token` / 学习式 `pos_embedding` / 分类头
2. torchvision 内部命名跨版本有差异（验证机 0.28 / AutoDL 0.16），
   整体严格加载会在版本不匹配时直接崩。逐块 try 可降级为部分加载并打印命中率

实测命中 **14/14**（patch 投影 + 12 块 + 末端 LayerNorm）。

> **保留意见**：预训练 ViT-B 是在 224×224 自然图像、16×16 语义 patch 上学的；
> 我们的 patch 只有 16×16 且覆盖公式笔画碎片，64px 高只有 4 行。
> 预训练特征的迁移效果可能不如预期。
>
> **此保留意见已在 §4.7 被实测证伪**——提高分辨率带来了大幅提升。

#### 解码器：标准 Transformer

按 §9.2 备选 A 的配置：`d_model=512, nhead=8, dim_feedforward=2048, num_layers=4, dropout=0.1`。
编码器输出 768 维经 `nn.Linear` 投影到 512。

**关键简化：Teacher Forcing 对新架构完全失效。**
Transformer 解码器训练是**单次并行前向 + 因果掩码**，不存在逐步喂入，
`TF_RATIO_START/END/EPOCHS` 三个配置只对 `cnn_lstm` 基线有效。
训练速度相比 LSTM 的 Python 逐步循环大幅提升（transformer 一步覆盖整个序列，
不再有 T 次 Python 循环）。

#### ⚠️ 训练/推理的张量对齐（踩过的坑，务必留意）

两套架构的**自然对齐方式本质不同**，硬凑成一个契约必然出错：

| | 解码器输入 | 位置 k 的预测 | 依赖 |
|---|---|---|---|
| `cnn_lstm` | 逐步喂 `targets[t-1]` | `targets[k]` | `targets[0..k-1]` |
| `vit_transformer` | `targets[:, :-1]`（即 `[SOS, t1, ..., t_{T-2}]`） | `targets[k+1]` | `targets[0..k]` |

因此对齐逻辑封装在 `FormulaRecognizer.training_step()` 里，按架构各自处理，
返回已对齐的 `(logits, targets)` 直接送 `CrossEntropyLoss`。

**曾经写错的方式**（症状极具迷惑性）：构造 `D = [SOS] + targets[:, :-1]` 让
`output[j]` 预测 `targets[j]`，看似满足旧契约，实则**上下文比解码时多一个 SOS**——
`output[1]` 看到的是 `[SOS, SOS]`，而贪心解码第一步只看到 `[SOS]`。
结果：**训练 loss 一路降到 0.03，推理 ExpRate 却是 0%**（训练时在抄答案）。
改用标准对齐后 ExpRate 0% → 100%。

`verify_pipeline.py` 的标签泄漏检查就是为这类错误准备的：
篡改 `targets[j:]` 后，位置 `k < j` 的输出必须逐元素不变。

#### 图像输入与 padding mask

`collate_fn` 把 batch 内图像右侧补白到最大宽度。ResNet 版本天然容忍（白边进卷积无影响），
但 Transformer 的交叉注意力会把这些白边 patch 也当有效位置。
`FormulaRecognizer.encode()` 会按图像像素宽度推出 patch 级 `key_padding_mask`，
交给解码器的 `memory_key_padding_mask`。

#### 参数量对比

| 架构 | 参数量 | 实测每步耗时（RTX 3060 Laptop，batch 12） |
|---|---|---|
| `vit_transformer` | 103.2M | ~220 ms |
| `cnn_lstm` | 24.5M | ~60 ms |

### 4.7 【实测】IMG_HEIGHT 是决定性的旋钮

这是本项目**单次改动收益最大**的一项，完整记录在此，避免重复推导。

#### 起因：从错误模式反推原因

H=64 训练完成后，CROHME ExpRate 只有 0.425。逐条看错误样例，发现模式极其一致：

| 预测 | 参考 | 错法 |
|---|---|---|
| `x = \frac{4}{5}` | `x = \frac{4}{3}` | 5 ↔ 3 |
| `y_1 = 7` | `y_1 = 1` | 7 ↔ 1 |
| `\frac{90}{19}` | `\frac{99}{19}` | 90 ↔ 99 |
| `b_{e}` | `b_{R}` | e ↔ R |

**结构和括号层级全对，只是认错了一个字符。** 这类"字形混淆"是分辨率不足的典型症状——
H=64/patch=16 时只有 **4 行 patch**，一个手写数字缩放后大约只占 1 个 patch。

#### 代价：比"高度翻倍"大得多

⚠️ **关键认知：图像是等比缩放的，高度翻倍意味着宽度也翻倍。**

| | H=64 | H=128 |
|---|---|---|
| patch 行 | 4 | **8** |
| patch 列（中位宽） | 16 | **31** |
| **patch 总数** | 64 | **248（4 倍，不是 2 倍）** |

实测耗时倍率：**2.14x**（每 epoch 255.6s → 547.1s）。
在 batch 8 上测得的倍率是 3.3x，但 batch 32 时矩阵更大、GPU 效率更高，实际倍率低得多——
**用大 batch 实测的倍率才可信**。

#### 宽度上限的连带调整

等比缩放后宽度也翻倍，原来的 `IMG_MAX_WIDTH=1200` 会让 **4.55% 的样本被压扁**。
但不能简单放宽——**ViT 注意力的显存是 O(patch²)**，实测外推（batch 32）：

| 宽度上限 | 峰值显存 | 压扁比例 |
|---|---|---|
| 1200 | ~14.5 GB | 4.55% |
| **1536（采用）** | **~18.5 GB** | **0.9%** |
| 2048 | ~24.5 GB | 0.10% ← 会 OOM |

选 **1536**：压扁比例与原来 H=64 时持平，显存留有余量。

#### 结果

| | H=64 | H=128 | 差 |
|---|---|---|---|
| CROHME eval ExpRate | 0.4249（80 轮最佳） | **0.5243** | **+0.099** |
| CROHME @epoch 10 | 0.2941 | **0.4148** | +0.121 |
| HME100K test ExpRate | 0.5832 | **0.6325** | +0.049 |
| HME100K test BLEU | 0.9117 | **0.9261** | +0.014 |

**H=128 只用 10 轮就追平了 H=64 跑满 75 轮的成绩。**

#### 诊断被验证

改造后，**当初那些具体的混淆全部消失**——同一批公式：

| 公式 | H=64 预测 | H=128 预测 | 参考 |
|---|---|---|---|
| x = 4/? | `\frac{4}{5}` ❌ | `\frac{4}{3}` ✅ | `\frac{4}{3}` |
| y₁ = ? | `y_1 = 7` ❌ | `y_1 = 1` ✅ | `y_1 = 1` |
| 2 = ?/? | `\frac{2}{3}` ❌ | `\frac{3}{7}` ✅ | `\frac{3}{7}` |

这不是"碰巧涨分"，而是**预测的失败模式被精准修复**。

**残余错误换了类型**：`S_{1}` vs `s_{1}`（大小写）、`M_{l}` vs `M_{1}`（字母 l 与数字 1）——
这类连人眼都易混，提高分辨率解决不了。

#### 平台期提前

H=128 在第 30 轮就见顶（H=64 是慢慢涨到第 75 轮），早停于第 40 轮。
**加轮数无用**，剩余提升要靠数据增强或架构改动。

#### 结论

- ✅ **`IMG_HEIGHT=128` 是当前配置的默认值**（见 `config.py`）
- ✅ 参考实现 pix2tex 用的也是 128 高度（`image_size=(128, 380)`），与本结论一致
- ⚠️ 代价是 2.14x 训练耗时，但可用更少的轮数抵消（40 轮 vs 80 轮，净耗时反而更少）
- 📌 **方法论**：从"错误模式"反推原因（而非盲目调超参）是本轮最有效的一步。
  如果当时先去调 batch size 或加轮数，大概率是白跑几十小时。


### 4.8 【实测】错误分析：剩余空间在哪里

H=128 之后目标已达成，但需要判断"还能不能便宜地再提升"。为此写了
`analyze_errors.py`，把预测错误自动归类，而不是凭几个样例猜。

#### ⚠️ 方法学陷阱：对齐方式会让结论差一个数量级

第一版统计用**逐位置 `zip` 比对**，得出"最常见的替换是 `}` → `{`，1253 次"，
据此判断"模型把括号方向搞反了"。改用 `difflib.SequenceMatcher` 做**真实编辑操作对齐**后：

| | zip 对齐（错误做法） | SequenceMatcher（正确） |
|---|---|---|
| `}` → `{` | "1253 次" | **82 条样本（占错误 0.9%）** |
| 错误性质 | 看起来是大量"替换" | 实际以**插入/删除**为主 |

**原因**：预测与参考长度不同时，`zip` 从分歧点往后全部错位，产生大量虚假的"替换对"。
而真实的错误绝大多数是插入/删除——`zip` 完全看不出来。

> **统计序列差异必须用编辑操作对齐，不能用逐位置 zip。**

#### 错误构成（HME100K test，24607 条）

| 类别 | 条数 | 占全体 | 占错误 |
|---|---|---|---|
| 完全正确 | 15633 | 63.53% | — |
| 仅大小写差异 | 257 | 1.04% | 2.86% |
| 仅形近字符差异 | 85 | 0.35% | 0.95% |
| 小错（≤2 token） | 5593 | 22.73% | **62.32%** |
| 中等错（≤5） | 1957 | 7.95% | 21.81% |
| 大错 / 结构错 | 1082 | 4.40% | 12.06% |
| **总错误** | **8974** | **36.47%** | |

#### 三个被实测否决的优化假设

| 假设 | 实测结果 | 判定 |
|---|---|---|
| 大小写 / l↔1 混淆是主要矛盾 | 占错误 **3.8%** | ❌ 性价比为零 |
| 括号方向搞反 | 占错误 **0.9%**（82 条） | ❌ |
| 括号配平后处理可挽回几个点 | 预测括号不配平的仅 **0.95% 样本**（234 条） | ❌ 天花板 <1 个点 |

原以为"加个括号配平模块"能拿几个百分点，**实测天花板是 +0.95 个点**，且是理论上限。

#### 真实的错误画像

**① 括号是"分组错"，不是"数量错"**

```
'{' → 漏掉  457 次        多出 '{'  402 次     ← 两个方向几乎对称
'}' → 漏掉  388 次        多出 '}'  378 次
```

漏与多的数量相近，说明模型**知道该有多少括号，只是放错了位置**。
佐证：**81.5% 的错误含括号，但只有 2.6% 括号不配平**。

例如该写 `\frac{a}{b c}` 却写成 `\frac{a b}{c}`——输出本身是**合法的平衡括号**，
没有任何信号提示"这里该断开"。**必须重看图才能判断，后处理无解。**

**② 数字与字形混淆（货真价实的视觉错误）**

```
3 → 2  124 次      2 → 1   75 次
2 → 3  117 次      5 → 3   75 次
3 → 5   80 次
```

与 H=64 时代那批"5↔3、7↔1"性质相同，只是量级小了一个数量级——
说明 H=128 大幅缓解但未根除视觉混淆。

**③ 零散观察：模型会凭空多出 `0`**

`<无> → '0'` 211 次，而 `'0' → <无>` 只有 92 次——**净多出 119 个**。
单向的系统性偏向，不是随机错误。成因不明，暂无法利用。

#### 结论：没有便宜的修复手段了

| 错误类型 | 规模 | 为什么不能便宜地修 |
|---|---|---|
| 括号分组错 | ~1625 次操作 | 输出是合法的平衡括号，后处理无从判断该在哪断开 |
| 数字 / 字形混淆 | ~471 次操作 | 需要重新看图，只能靠模型能力 |
| 大小写、`.`↔`\cdot` | ~300 次 | 占比太小，且部分本身有歧义 |

剩下的路只有**重训实验**（更高分辨率 / 更大容量 / 更多数据），都是几小时起步、收益不确定。

> **方法论价值**：本轮"先测量再动手"至少避免了三次白工——弹性形变增强（约 5h）、
> 括号后处理（约 2h）、大小写规则（约 1h）。若按直觉一路做下去，
> 最后会发现每个只换来零点几个点，还会误以为"方法无效"。
>
> **可靠的信号是"错误模式的一致性"**：H=64 那批错误"5↔3、7↔1"在样例里压倒性一致，
> 所以"分辨率不足"的判断成立并被验证；而"大小写"只来自 2 个样例，就完全站不住。
> **样例数量不足时不要下结论——先统计。**

## 7. 训练策略

### 7.1 超参数配置

| 参数 | 值 | 说明 |
|------|------|------|
| **Batch Size** | 32（或梯度累积到等效 64） | RTX 3090 可承载 |
| **学习率** | 1e-4 ~ 5e-4 (peak) | Encoder 1e-4，Decoder 5e-4 分层 |
| **Warmup** | 1000~5000 steps（或 5 epochs） | 线性 warmup |
| **Min LR** | 1e-6 | Cosine 底部 |
| **Optimizer** | AdamW | weight_decay=0.01~0.05 |
| **LR Schedule** | Cosine Annealing | T_max=50 |
| **Epochs** | 50 ~ 100 | 依早停决定（CROHME 50~100, HME100K 20~40） |
| **Teacher Forcing** | 1.0 → 0.3 | 线性衰减 |
| **Gradient Clip** | max_norm=1.0 | 防梯度爆炸 |
| **Dropout** | 0.1 ~ 0.3 | Decoder 内 |
| **Label Smoothing** | 0.1 | 防过拟合，提升泛化 |
| **混合精度** | FP16（AMP） | 显存减半，训练加速 |

### 7.2 训练流程

```
                    ┌─────────────────┐
                    │  预训练 Encoder  │
                    │  (ImageNet 权重) │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
       阶段1: 预训练    阶段2: 联合训练    阶段3: 微调
       冻结 Encoder     全网络训练        降低 LR
       仅训练 Decoder   TF ratio=0.7~0.3  LR×0.1
       10 epochs        30~50 epochs      10~20 epochs
```

### 7.3 损失函数

```python
# 交叉熵损失 + Label Smoothing（忽略 padding token）
criterion = nn.CrossEntropyLoss(ignore_index=PAD_TOKEN, label_smoothing=0.1)

# 混合精度训练（AMP）—— 显存减半，速度提升
from torch.cuda.amp import autocast, GradScaler
scaler = GradScaler()
with autocast():
    output = model(images, targets)
    loss = criterion(output.view(-1, vocab_size), targets.view(-1))
scaler.scale(loss).backward()
scaler.unscale_(optimizer)
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
scaler.step(optimizer)
scaler.update()
```

### 7.4 早停策略

**监控 `(ExpRate, BLEU)` 复合判据**，patience=10 epochs：

```python
# best_exprate / best_bleu 初始化为 -1.0，而不是 0.0
if (val_exprate, val_bleu) > (best_exprate, best_bleu):
    best_exprate, best_bleu = val_exprate, val_bleu
    save_checkpoint('best.pth')
    patience_counter = 0
else:
    patience_counter += 1
    if patience_counter >= PATIENCE:
        print("Early stopping triggered")
        break
```

> **为什么必须用复合判据，不能只盯 ExpRate**：
> - ExpRate 是**离散指标**，训练早期可能连续多轮都是 0。
>   若初始化为 0.0 用 `>` 比较，`0.0 > 0.0` 恒为假 —— **best.pth 永远不会被保存**
>   （用连续值的 BLEU 时不会暴露这个问题，改指标后才会踩到）。
> - 同理，若早停计数只按 ExpRate 重置，会在第 10 轮就误触发早停，
>   把还在爬坡的训练掐死。
>
> `best.pth` 的选择与早停计数都基于这个复合判据，ExpRate 主导、BLEU 同分决胜。

## 8. 评估方案

### 8.1 评估指标实现

**主指标是表达式准确率 ExpRate**，其余为辅助参考（`utils.py` 中实现）。

| 指标 | 实现方式 | 说明 |
|------|----------|------|
| **表达式准确率（主）** | `pred_latex == gt_latex` 精确匹配 | 最严格、最贴近"能不能用" |
| **BLEU-4** | `nltk.translate.bleu_score.corpus_bleu` | 语料库级别 BLEU，辅助参考 |
| **编辑距离** | 内置 Levenshtein 实现（无额外依赖） | 字符串相似度 |
| **Token 准确率** | 逐 token 对比 | 训练过程监控 |

> **为什么主指标从 BLEU 改成 ExpRate**：BLEU 对公式这类**结构性序列**偏弱——
> 一个符号位置错、一层括号错，BLEU 可能仍然很高，但公式已经完全不可用。
> ExpRate 直接回答"识别对不对"，是 MER 领域的标准口径。
>
> **注意 ExpRate 是离散指标**：训练早期它可能连续多轮都是 0，
> 因此早停计数与 `best.pth` 选择都采用 `(ExpRate, BLEU)` 复合判据，
> BLEU 只在 ExpRate 同分时决胜。若严格只盯 ExpRate，
> 会在前 10 轮就误触发早停，把还在爬坡的训练掐死。

### 8.2 BLEU 计算细节

```python
from nltk.translate.bleu_score import corpus_bleu, SmoothingFunction

def compute_bleu(predictions, references):
    """
    predictions: list of predicted LaTeX strings
    references: list of list of reference LaTeX strings (可多个参考)
    """
    # 分词：按字符级或 token 级
    pred_tokens = [tokenize(pred) for pred in predictions]
    ref_tokens = [[tokenize(ref)] for ref in references]

    # 使用 smoothing 防止短序列 BLEU=0
    smoother = SmoothingFunction().method1
    bleu = corpus_bleu(ref_tokens, pred_tokens, smoothing_function=smoother)
    return bleu
```

### 8.3 评估协议

```
CROHME 2019 测试集评估：
├── 计算 corpus-level BLEU-4
├── 计算平均编辑距离
├── 计算表达式完全匹配率
├── 分公式长度区间统计（短<20, 中20-50, 长>50 tokens）
└── 分符号类型统计（希腊字母、运算符、函数等）
```

### 8.4 目标指标（基于业界参考）

| 指标 | CNN+LSTM 基线 | 目标 | ViT+Transformer SOTA | 本项目预期 |
|------|---------------|------|---------------------|-----------|
| **表达式准确率（主）** | 50~60% | **> 50%** | 78~92% | 60~70% |
| BLEU-4 | 0.80~0.85 | > 0.85 | 0.90~0.93 | 0.85~0.90 |
| 编辑距离 (↓) | 0.10~0.15 | < 0.15 | 0.03~0.06 | 0.08~0.12 |
| 推理速度 | - | < 500ms | ~100ms | ~200ms |

> 参考：Pix2Tex 在标准评测上 BLEU ~85-87；CoMER (2024) 在 CROHME 上 ExpRate ~78%。
> CoMER 的 78% 是当前 CROHME 上的较强水平，可作为 ExpRate 目标的参照上界。
> BLEU 0.85 是"strong performance"水平，0.90+ 需要精细调参和更大模型容量。

## 9. 风险与备选方案

### 9.1 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| CROHME 下载失败 | 中 | 高 | 优先使用 HME100K，CROHME 作为补充 |
| BLEU 无法达到 0.85 | 中 | 高 | 升级 Decoder 为 Transformer；使用 Pix2Tex 预训练权重 |
| 长公式解码质量差 | 高 | 中 | 使用 Beam Search；增加最大序列长度 |
| 显存不足 | 低 | 中 | 降低 batch size；梯度累积 |
| 过拟合 | 中 | 中 | 增加 Dropout；数据增强；权重衰减 |

### 9.2 备选技术路线

> **落地情况**：备选 A + 备选 C 已合并实现为默认架构 `vit_transformer`（详见 §4.6）；
> 备选 B（Pix2Tex 微调）未采用。原备选 A 的配置被原样沿用。

#### 备选 A：Transformer Decoder（若 LSTM 效果不足）—— ✅ 已实现

```python
# 与最终实现一致（model.FormulaTransformerDecoder）
decoder_layer = nn.TransformerDecoderLayer(
    d_model=512, nhead=8, dim_feedforward=2048, dropout=0.1
)
decoder = nn.TransformerDecoder(decoder_layer, num_layers=4)
```

优势：长序列建模更强，自注意力机制全局感知
代价：显存增加约 2x，训练速度下降

> **实现时的两点补充（规划时未预见）**：
> 1. **Teacher Forcing 调度对新架构完全失效**——Transformer 解码器训练是
>    单次并行前向 + 因果掩码，不存在逐步喂入，`TF_RATIO_*` 只对基线有效。
> 2. **张量对齐必须特别处理**——两套架构的自然对齐方式不同，硬凑成一个契约
>    会导致标签泄漏（训练 loss 极低但推理 ExpRate 为 0）。详见 §4.6。

#### 备选 B：迁移 Pix2Tex 预训练权重 —— ❌ 未采用

```python
# 加载 Pix2Tex 预训练模型，在 HME100K 上微调
from pix2tex import LatexOCR
model = LatexOCR()
# 微调最后几层...
```

优势：开箱即用，BLEU 可直接达标
代价：无法完全自定义架构，学习意义降低

未采用的原因：本项目希望通过完整实现掌握端到端流程，直接套用现成模型会失去这个价值；
且 Pix2Tex 词表很小（~80），对 HME100K 覆盖不足。

#### 备选 C：ViT Encoder + 自回归 Transformer Decoder —— ✅ 已实现（默认架构）

将 Encoder 升级为 ViT 或 Swin Transformer，Decoder 升级为自回归 Transformer。
这是当前 SOTA 路线（如 UniMERNet）。

**实际实现选择了自写 ViT + 复用 torchvision 预训练权重**，而非 Swin 或现成 ViT——
原因是 torchvision 的 ViT 固定尺寸、无法处理宽高比高达 16:1 的公式图像（详见 §4.6）。
